# 青训营后端

## 一、Go 语言基础

### 1.1 基本语法
- **变量声明**: `var name string` / `name := "xxx"`（短变量声明）
- **基本类型**: bool, string, int/uint(8/16/32/64), float32/64, complex64/128, byte, rune
- **控制流**: if-else, for（Go 只有 for，没有 while），switch（默认带 break）
- **函数**: 支持多返回值 `func div(a, b int) (int, error)`
- **defer**: 延迟执行，在函数返回前执行，后进先出（LIFO）

### 1.2 复合类型
- **数组**: `arr := [3]int{1,2,3}` — 固定长度
- **切片**: `s := []int{1,2,3}` — 动态数组，底层数组指针 + len + cap
- **map**: `m := make(map[string]int)` — 哈希表，需用 make 初始化
- **struct**: 自定义类型 `type User struct { Name string; Age int }`
- **指针**: `*T` 取指针，`&` 取地址，Go 指针不支持算术运算

### 1.3 接口与错误处理
- **接口(interface)**: 鸭子类型，隐式实现
  ```go
  type Reader interface { Read(p []byte) (n int, err error) }
  ```
- **空接口**: `interface{}` / `any` — 任意类型
- **错误处理**: Go 没有 try-catch，通过返回值传递错误
  ```go
  if err != nil { return err }
  ```
- **panic/recover**: 用于异常情况，recover 仅在 defer 中有效

### 1.4 并发编程
- **goroutine**: 轻量级线程，`go func()`
- **channel**:
  - 无缓冲: `ch := make(chan int)` — 同步阻塞
  - 有缓冲: `ch := make(chan int, 10)` — 异步
  - `close(ch)` 关闭通道
- **select**: 多路复用，同时监听多个 channel
- **sync 包**: Mutex, RWMutex, WaitGroup, Once, Cond, Pool
- **Context**: 超时控制、取消信号、传值，`context.Background()` / `context.WithCancel()` / `context.WithTimeout()`

### 1.5 常用标准库
- **fmt**: 格式化 I/O
- **net/http**: HTTP 客户端/服务端
- **encoding/json**: JSON 序列化/反序列化
- **io / os / bufio**: 文件与 I/O 操作
- **time**: 时间处理
- **strings / strconv**: 字符串处理与类型转换

## 二、Web 框架

### 2.1 Gin
- **特点**: 高性能、轻量级、中间件机制、路由分组
- **路由**:
  ```go
  r := gin.Default()
  r.GET("/user/:id", handler)
  r.POST("/user", handler)
  ```
- **中间件**: `r.Use(gin.Logger(), gin.Recovery())`，自定义中间件返回 `gin.HandlerFunc`
- **参数绑定**: `ShouldBindJSON(&user)` / `ShouldBindQuery(&params)`
- **响应**: `c.JSON(200, gin.H{"msg": "ok"})`

### 2.2 Hertz (字节跳动自研)
- **特点**: 超高性能、云原生设计、支持 HTTP/1.1/2、扩展性强
- **核心概念**: Engine → Route → HandlerFunc → Context
- **中间件**: Hertz 的中间件链与 Gin 类似，支持 `c.Next()`
- **协议层**: 可插拔协议，支持 HTTP/1.1、HTTP/2、WebSocket
- **性能优化**: 零拷贝、对象池、复用内存，吞吐量优于 Gin

### 2.3 对比
| 特性 | Gin | Hertz |
|------|-----|-------|
| 性能 | 优秀 | 更优（字节自研优化） |
| 社区 | 大 | 中（字节生态） |
| 扩展 | 中间件丰富 | 协议可插拔 |
| 适用 | 通用项目 | 字节内部 / 高并发 |

## 三、数据库

### 3.1 MySQL
- **ORM (GORM)**:
  - AutoMigrate 自动建表
  - CRUD: `Create`, `Find`, `Where`, `Updates`, `Delete`
  - 关联查询: BelongsTo, HasMany, ManyToMany
  - 链式调用 + 预加载 `Preload`
- **事务**: `db.Transaction(func(tx *gorm.DB) error { ... })`
- **索引优化**:
  - B+Tree 索引，最左匹配原则
  - 合理设计索引，避免回表
  - 慢查询分析：EXPLAIN 查看执行计划
- **SQL 优化**:
  - 避免 SELECT *
  - 合理使用 JOIN 代替子查询
  - LIMIT + 覆盖索引优化分页
  - 批量插入用 VALUES 多行

### 3.2 Redis
- **数据结构**:
  - String: 缓存、计数器
  - Hash: 对象存储
  - List: 消息队列（LPUSH/BRPOP）
  - Set: 去重、交集/并集
  - ZSet: 排行榜（有序集合）
- **Go 客户端 go-redis**:
  ```go
  rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
  rdb.Set(ctx, "key", "value", 0)
  rdb.Get(ctx, "key")
  ```
- **持久化**: RDB（快照）、AOF（追加日志）
- **高可用**: 主从复制 + Sentinel / Redis Cluster
- **缓存策略**: 过期时间 TTL、内存淘汰（LRU/LFU）、缓存穿透/击穿/雪崩解决方案

## 四、RPC 框架

### 4.1 Kitex (字节跳动自研)
- **特点**: 基于 Thrift/Protobuf 的高性能 RPC 框架
- **核心概念**:
  - IDL（接口定义语言）— Thrift / Protobuf
  - 代码生成 — `kitex -module xxx service.thrift`
  - Client / Server 分离
- **使用流程**:
  1. 编写 IDL 文件定义 Service & Struct
  2. 运行 kitex 工具生成代码
  3. 实现 Server 端的 Handler
  4. Client 端发起调用
- **特性**:
  - 支持多种网络协议（TTHeader, HTTP2, gRPC）
  - 连接复用 + 连接池
  - 超时控制、重试、熔断
  - 可观测：链路追踪（OpenTelemetry）、Metrics

### 4.2 RPC 关键概念
- **序列化**: Thrift (Binary/Compact) vs Protobuf，Compact 协议体积更小
- **服务发现**: 结合 ETCD / Nacos / Consul
- **负载均衡**: 随机、轮询、加权、一致性哈希
- **超时 & 重试**: 默认超时 + 指数退避重试

| 特性 | Kitex | gRPC |
|------|-------|------|
| 通信协议 | Thrift/Protobuf | Protobuf |
| 语言绑定 | Go 优先 | 多语言 |
| 性能 | 极高（字节优化） | 高 |
| 治理能力 | 内置丰富 | 需扩展 |

## 五、消息队列

### 5.1 常见 MQ
| 组件 | 特点 | 适用场景 |
|------|------|---------|
| Kafka | 高吞吐、持久化、分区 | 日志收集、大数据管道 |
| RabbitMQ | 稳定、灵活路由 | 任务队列、微服务通信 |
| RocketMQ | 事务消息、延迟队列 | 订单、交易场景 |
| BMQ (字节自研) | 高性能、低延迟 | 内部使用 |

### 5.2 消息模型
- **点对点 (Queue)**: 一条消息一个消费者消费
- **发布订阅 (Topic)**: 一条消息多个消费者订阅
- **消费者组**: 同一个 Group 内的消费者竞争消费分区

### 5.3 核心概念
- **Producer**: 消息生产者
- **Consumer**: 消息消费者（Push / Pull 模式）
- **Broker**: 消息存储与转发节点
- **Partition**: Kafka 分区，并行消费的基础
- **Offset**: 消费偏移量，控制消息进度

### 5.4 消息可靠性
- **生产者**: ACK 机制（0/1/all）
- **Broker**: 多副本（Replica）保证持久化
- **消费者**: 手动 ACK / 自动 ACK，业务处理完再提交 Offset
- **重试队列 & 死信队列**: 处理消费失败的消息

## 六、微服务架构

### 6.1 架构演进
- **单体架构**: 所有功能在一个进程中，部署简单但耦合严重
- **垂直拆分**: 按业务模块拆分为独立服务
- **微服务**: 每个服务独立部署、独立数据库、独立团队
- **服务网格 (Service Mesh)**: 将通信逻辑下沉到 Sidecar 代理

### 6.2 微服务核心组件
- **服务注册与发现**: ETCD / Nacos / Consul / Eureka
- **配置中心**: Nacos / Apollo / 配置中心统一管理配置
- **API 网关**: 统一入口，路由、限流、鉴权、日志
- **负载均衡**: 客户端（Ribbon）或服务端（Nginx/K8s Service）
- **熔断降级**: 防止服务雪崩（Hystrix / Sentinel / 自研）
- **链路追踪**: 全链路请求追踪（Jaeger / Zipkin / OpenTelemetry）

### 6.3 字节跳动微服务体系
- **服务框架**: Kitex (RPC) + Hertz (HTTP)
- **服务治理**: 自研服务治理平台
- **配置管理**: 自研配置中心
- **监控**: Prometheus + Grafana + 自研监控系统

### 6.4 分布式事务
- **CAP 理论**: 一致性、可用性、分区容忍性，三者不可兼得
- **BASE 理论**: Basically Available, Soft State, Eventually Consistent
- **解决方案**:
  - 两阶段提交 (2PC) — 强一致，性能差
  - TCC (Try-Confirm-Cancel) — 业务补偿
  - 本地消息表 + 消息队列 — 最终一致
  - Seata AT 模式 — 自动补偿

## 七、云原生

### 7.1 容器化
- **Docker**: 镜像打包，`Dockerfile` 定义构建步骤
  - 多阶段构建减少镜像体积
  - `.dockerignore` 排除不必要的文件
- **Kubernetes (K8s)**:
  - Pod: 最小调度单元
  - Service: 服务发现与负载均衡
  - Deployment: 声明式更新与扩缩容
  - ConfigMap / Secret: 配置管理

### 7.2 持续集成/持续部署 (CI/CD)
- **GitHub Actions / GitLab CI**: 自动化构建、测试、部署
- **Pipeline 阶段**: 代码检查 → 单元测试 → 构建镜像 → 部署到 K8s
- **蓝绿部署 / 灰度发布**: 减少发布风险，逐步切换流量

### 7.3 可观测性 (Observability)
- **日志 (Logging)**: 结构化日志（JSON格式），集中采集（ELK / Loki）
- **指标 (Metrics)**: Prometheus + Grafana，RED 方法（Rate/Errors/Duration）
- **链路追踪 (Tracing)**: OpenTelemetry + Jaeger，TraceID 串联全链路

### 7.4 服务网格 (Service Mesh)
- **Istio**: 主流的 Service Mesh 实现
- **Sidecar 模式**: Envoy 代理拦截所有进出流量
- **功能**: 流量管理、安全认证、可观测性，业务代码无需感知

### 7.5 字节跳动云原生实践
- **微服务规模**: 数万个服务实例
- **容器编排**: 自研调度系统（兼容 K8s 生态）
- **服务网格**: 大规模落地 Sidecar 模式
- **中间件云原生化**: 数据库、缓存、MQ 全托管

## 八、青训营项目实战要点

### 8.1 项目选型
- 后端框架: Hertz（推荐）或 Gin
- RPC 框架: Kitex（微服务间通信）
- ORM: GORM
- 缓存: Redis
- 数据库: MySQL
- 消息队列: Kafka 或 RocketMQ

### 8.2 项目结构
```
project/
├── cmd/            # 启动入口
├── internal/       # 业务逻辑
│   ├── handler/    # 请求处理
│   ├── service/    # 业务层
│   ├── repository/ # 数据访问
│   └── model/      # 数据模型
├── kitex_gen/      # Kitex 生成代码
├── idl/            # IDL 定义
├── config/         # 配置文件
├── pkg/            # 公共工具
└── go.mod
```

### 8.3 常见问题与解决方案
- **缓存一致性**: 先写 DB 再删缓存（Cache-Aside 模式）
- **热点 Key**: 本地缓存 + 分布式缓存双层架构
- **接口幂等性**: 唯一请求 ID + 去重表
- **并发安全**: 分布式锁（Redis SETNX / Redlock）
- **大事务**: 拆分为小事务，异步化处理
